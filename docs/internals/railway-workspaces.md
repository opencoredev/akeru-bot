# Railway workspace adapter

Railway workspaces run through Sandbox SDK's `railway()` provider (`@opencoredev/sandbox-sdk/railway`, which wraps the official `railway` package). `apps/server/src/provider/workspace/SandboxProviders.ts` builds it with explicit `RAILWAY_API_TOKEN` and `RAILWAY_ENVIRONMENT_ID` values from the environment's sandbox settings, never ambient process credentials. The token follows the existing secret-store and client-redaction path. See [sandbox workspaces](sandbox-workspaces.md) for the shared session, identity, and pool rules.

The shared identity file persists the Railway sandbox ID. It is written from inside the provider's `create`, before the SDK builds its handle. Reattachment uses `connectSandbox` with the saved ID; unavailable identities fail closed without creating a replacement. The SDK reports a running VM as `running` and every other status as `stopped`; Akeru maps `stopped` to sleeping and only the SDK's `not_found` error to missing. Authorization and network failures propagate.

Railway identity hashes exclude the credential fingerprint while pool keys retain it. Rotating credentials creates a fresh SDK client but reconnects to the same saved VM, including after a server restart. Changing environments or revoking access fails closed rather than abandoning the old identity and creating a second billable VM. Settings requires explicit acknowledgement of the Railway-dashboard retirement path before replacing or removing existing credentials; this is not automatic remote cleanup.

The workspace pool serializes Railway acquisition and release by durable identity across credential-scoped clients. A destroy request waits for the final identity lease, invalidates idle clients, and deletes the VM once. Shutdown waits for pending identity operations and deduplicates deletion. Creation after deletion starts a fresh lifecycle; stale clients cannot reattach from the idle cache.

Railway's SDK provider has no `pause` capability. Workspace-pool release is therefore nondestructive: sleep is a no-op, wake verifies the VM is running and otherwise fails (`stoppedWake: "fail"`), and destroy deletes the VM before the shared wrapper removes its identity file. The provider does declare `snapshot` (Railway disk checkpoints), but checkpoints are not a substitute for pause/resume: restoring one creates a different VM and cannot transparently preserve the saved identity. No checkpoint API is added to the common workspace contract.

Commands run through the SDK handle's `run`, with Akeru's shell quoting and cwd, environment, and millisecond timeouts passed as SDK options. A command the SDK reports with a null exit code is treated as failure, never successful execution.

Browser endpoint resolution fails explicitly because Railway previews require CLI tunnels. Railway creations declare no preview ports, so no public domain is created. Private network addresses must not be returned as client-accessible preview URLs. There is no automatic tunnel process or local/remote origin assumption in this adapter.

Browser-dependent MCP connectors are rejected before a Railway workspace lease is acquired, so unsupported browser setup cannot invoke destructive acquisition-failure cleanup on a durable VM.

Railway session-setup and workspace-wake failures never destroy the VM. Multiple credential-scoped clients may refer to one durable identity, so a failed new client must not invalidate another active session. A wake failure drops only the in-memory handle; the next acquire, or the pool's cleanup if none comes, reconnects by saved ID. That cleanup takes the identity lock that creation and deletion take, and only reattaches to the VM the entry lost, so it never keeps a handle to a deleted VM or creates a new one. Cleanup deduplicates by provider ID, not identity: two handles are the same VM only when their IDs match. Shutdown deletes each VM once: after one credential key's deletion, it forgets the identity's other detached keys that lost that same VM instead of reattaching them. A key detached from a different VM, such as a replacement created after someone deleted the original, is still reattached and deleted, and an explicit deletion through another key's lease deletes it too. Explicit workspace destruction remains destructive. The retirement confirmation stores only a Railway save/disconnect action and applies it to current settings, preserving unrelated changes received while the dialog is open.
