# Sandbox workspaces

Remote bot workspaces run on [Sandbox SDK](https://sandbox-sdk.app) (`@opencoredev/sandbox-sdk`). One implementation of `AkeruRemoteSession` covers every provider; provider differences live in a small binding table.

## Pieces

- `apps/server/src/provider/workspace/SandboxProviders.ts` maps each `RemoteBotSandbox` to a `SandboxBinding`: the configured SDK provider, built from explicit credentials in sandbox settings, plus the rules the SDK cannot express. Those rules are the browser policy (`private`, `public`, `loopback`, or `none` with a reason; a `loopback` preview sets `AkeruBrowserEndpoint.loopback`, so the browser attachment is withheld from hosted connectors, as for a local workspace), what wake does with a stopped sandbox on a provider without `pause` (`fail`, `on-use`, or a native start), ports to declare at creation, and Daytona's desktop hook.
- `apps/server/src/provider/workspace/SandboxSession.ts` turns an SDK `Sandbox` handle into an `AkeruRemoteSession`. `run` uses `box.run`, files use `box.files`, `inspect` reads `provider.connect(id).state`, and `sleep`/`wake` call `pause`/`resume` only when the handle has the `pause` capability.
- `apps/server/src/provider/botWorkspaceFilesystem.ts` is the Mastra filesystem over `box.files`. Copy, move, and `mkdir` run as commands because the SDK file API has no equivalent.
- `apps/server/src/provider/workspace/AsciiProvider.ts` is a custom SDK provider for Ascii Box, which Sandbox SDK does not ship. It implements the `/provider` contract over `@asciidev/box-sdk`, with files sent as base64 commands.

## Working directory

New identities record `workdir: "/workspace"`, the SDK's default. An identity without `workdir` was written by a pre-migration adapter, whose commands ran in the provider's own default directory. On the first reattach Akeru resolves that directory once and saves it: the way each old adapter ran commands (`SandboxBinding.legacyWorkdir`): a bare `pwd` through the native SDK for Vercel, Upstash, Railway, Tenki and Ascii Box, and Daytona's `getWorkDir()` (Dockerfile `WORKDIR`, else home). E2B's old adapter ran as E2B's default `user` while the SDK runs as root, so its home is read from the passwd database and the user is recorded too (see below). The probe runs a guest command, so reattach first wakes the sandbox the way its session would (resume, or Daytona's start). If waking, the probe, or saving the identity fails, reattach fails closed and the identity is left unchanged. If reattach resumed the sandbox itself, by waking it or during adoption, it pauses it again before reporting the failure, because no lease exists yet to put it back to sleep. The sandbox counts as woken from the moment the wake starts it, so a resume that starts the VM and then fails to finish (legacy Tenki's wait for readiness) still pauses it. A Daytona sandbox it started has no SDK pause and is left to Daytona's auto-stop. `SandboxSession.run` resolves `cwd` against the workdir, and `BotWorkspaceFilesystem` resolves every path against it before file calls and commands.

Sandbox SDK finds Railway and Upstash sandboxes through metadata it writes when it creates them (`/tmp/.sandbox-sdk/railway.json`, and `SANDBOX_SDK_UPSTASH_METADATA` or `/tmp/.sandbox-sdk/upstash.json`). The old adapters never wrote it, and the SDK reports such a sandbox as `not_found`. `workspace/SandboxAdoption.ts` handles that: when an SDK call fails with `not_found` or `file_not_found`, Akeru asks the provider's own SDK whether the sandbox exists. If it does, Akeru writes the metadata only where none is present (resuming a paused Upstash box first) and retries once. Only the provider's own answer that the sandbox is gone counts as gone; a second `not_found` on an existing sandbox is reported as `unavailable`. Reattach, `inspect`, and the create-failure cleanup check all go through this path.

Tenki cannot be adopted this way: the SDK requires session metadata, and Tenki has no API to change an existing session's metadata. When the SDK refuses a saved Tenki session as `not_found`, reattach falls back to `SandboxBinding.legacy`, a binding over the shim provider. The shim reports `not_found` for a terminated session, so reattach still fails closed. The shim and the Ascii Box shim share `workspace/ShellFiles.ts` for file calls.

Where an SDK's `connect` wakes a paused sandbox (E2B, Upstash), the binding's `peek` reads the state without side effects. `inspect` uses it instead of `connect`, and reattach reads it before connecting. A sandbox that was paused or stopped counts as woken by the reattach from that moment, before `connect` runs, because `connect` can resume it and then fail; any failure from there on pauses it again (best effort, logged if the pause fails).

For a legacy E2B sandbox, `identity.user` is `user`. `SandboxSession.run` wraps each command in `su -s /bin/sh -c '<command>' user`, which keeps the SDK's working directory and environment. `BotWorkspaceFilesystem` stages each write or append in a `/tmp` directory that user creates with mode `0700`, so no other guest account can read the payload, then runs `cat` as that user, so new files keep the tree's owner. Reads, listings and file deletes use the SDK's root file API. A non-recursive `rmdir` runs the guest `rmdir` command on every provider, because the shell-backed providers' non-recursive remove is `rm -f`, which refuses directories. Without this, root-owned files would land in a `user`-owned tree, which tools such as git refuse to work in.

## Saved sandbox IDs

`createRemoteBotWorkspace` writes the identity file from inside a wrapper around the provider's `create`, right after the provider returns the new ID and before `createSandbox` builds the handle. Sandbox SDK 1.0.3 drops the ID when handle setup and its own cleanup both fail ([opencoredev/sandbox-sdk#35](https://github.com/opencoredev/sandbox-sdk/issues/35)); writing it first means Akeru always has it.

- If the identity write fails, the wrapper deletes the new sandbox and the error names its ID.
- If the provider's own `create` rejects after allocating a sandbox it could not delete (Railway initializes the VM inside `create` and deletes it on failure), the SDK error carries `sandboxId`. Akeru saves that ID with `cleanup: true`. The next open deletes that sandbox before creating a new one, and keeps the ID and creates nothing while deletion fails.
- If anything later fails, the identity file is removed only when `provider.connect` answers `not_found`. Any other answer keeps the ID, and the next session reattaches to that sandbox.
- `destroy` removes the identity file only after the provider deletes the sandbox, and only while the file still names that sandbox. A stale handle to a deleted sandbox leaves a file that names its replacement.
- A saved ID that cannot be reattached fails closed with a message naming the identity file; Akeru never creates a replacement on its own.

`botWorkspace.sandboxSdk.test.ts` exercises these paths against the SDK's `memory()` provider.

## Appends

`BotWorkspaceFilesystem.appendFile` stages the payload through the SDK's file API, then runs one guest script that holds a lock keyed by the target path, appends with `cat -- staged >> target`, and releases the lock. `cat` writes in pieces and O_APPEND only keeps each write whole, so the lock is what keeps concurrent appends from different sessions apart. Where `flock` exists, the lock is a `/tmp` file the kernel unlocks when its holder exits, so a dead holder never blocks anyone and no stale cleanup exists. Without `flock`, the lock is `mkdir` of that path plus `.d`, and it is never broken: an append that cannot take it within the wait (60 seconds by default) fails with exit 75 and an error naming the file, rather than removing a lock that may belong to a live session. Appends through one workspace also queue in-process. On the shell-backed providers (Ascii Box, legacy Tenki), a write with a mode creates the file under `umask 077` before the payload lands and only then applies the requested mode, so a staged payload in `/tmp` is never readable by another guest account. The staged file is removed through the SDK afterwards, and a failed final append is reported, not retried. `botWorkspaceFilesystem.shell.test.ts` runs both lock paths with a real `/bin/sh` against a temp directory, hiding `flock` from `PATH` for the fallback.

## Pool rules

`AkeruBotWorkspace.capabilities` (`pause`, `snapshot`, `browser`, `reconnect`) comes from the session. `BotWorkspacePool` drops the handle of a reattachable workspace whose wake fails, so the next acquire reconnects by saved ID. The wake may already have resumed the sandbox, so the pool keeps a detached entry for it until a reconnect succeeds and the pool holds the live workspace: if no acquire comes first, or the reconnecting acquire also fails, the pause retry or `destroyAll` reattaches and pauses or deletes it. Cleanup never creates a sandbox: it passes the key's creator a reattach request (`BotWorkspaceReattach`) naming the provider ID the entry lost, and `createBotWorkspace` resolves nothing when no sandbox is saved, the saved one is a different sandbox, or it is left by a failed setup. The pool then drops the entry. A cached browser is tied to the workspace it was built for, so when the pool hands out a replacement workspace, `AkeruSessionResources` closes that browser and builds a new one against the replacement's computer. The pool also keeps workspaces that fail to pause so the pause can be retried. Workspaces without `pause` sleep as a no-op. Failed session setup never destroys durable sandboxes (`DURABLE_REMOTE_SANDBOXES`: Railway, Tenki, Ascii Box, Boat, Local Docker), and never destroys a workspace another acquisition holds or has used. `BotWorkspaceLease.unshared()` is true only for the sole lease the pooled entry has granted since it opened, on a workspace created for it (`AkeruBotWorkspace.created`, `false` after a reattach by saved ID) rather than woken from sleep; anything else is released, not destroyed. A failed setup releases with `destroy: "ifUnshared"`, so the pool checks ownership when it accepts the release, after the chat's own cleanup, and a chat that joined during that cleanup keeps the workspace. Vercel routes only ports declared at creation, so `SandboxBinding.routePort` adds a missing port through the native `Sandbox.update` before a preview. `update` replaces the whole port list, so the binding reads the list fresh from Vercel and runs one port change at a time per sandbox in this process. Railway keeps its identity coordination; see [Railway workspaces](railway-workspaces.md).

## Known gaps

- Daytona has no SDK pause. Akeru relies on Daytona's auto-stop and starts the sandbox through `provider.api` on wake.
- Analytics reports Boat and Local Docker as `other` until the usage schema adds them.
